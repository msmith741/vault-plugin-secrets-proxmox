# Security model and acceptance checklist

The plugin issues finite-lived Proxmox API tokens for **one restricted Proxmox user per Vault mount**. The user authenticated by the mount must be identical to the user and realm selected by the Vault role. Cross-user issuance is prohibited **before the API call**, independently of Proxmox's permission settings.

## Confirmed privilege-escalation finding

Tests against a disposable container running **real Proxmox VE 9.2.2** found that a non-root API-token issuer granted `PVEUserAdmin` on `/access` could mint an authenticating API token for `root@pam`. Realm-scoped grants tested on `/access/realm/pve` were insufficient for cross-user token creation.

This is not a Proxmox CVE or a flaw in the documented ACL model. It is a dangerous **issuer design**: global user-administration access is incompatible with a narrow automation identity. **Do not grant global PVEUserAdmin to make cross-user token creation work.**

The same real-container test confirmed:

- Two distinct restricted PVE-realm users, each authenticating through their **own password ticket**, successfully generated and revoked their own temporary tokens using separate Vault mounts.
- Vault refused a credential request when a role targeted any user other than its mount's issuer, including attempts using an intentionally overprivileged API-token issuer.
- A short-lived workload token with `PVEAuditor` permissions was denied the ability to create a longer-lived sibling token (HTTP 403).
- Real token expiration remained effective after Vault was not involved; revocation worked after role modification.
- The prior global-issuer approach was still able to create an authenticating `root@pam` API token directly through Proxmox. The disposable probe was immediately deleted.

See [real Proxmox testing](real-proxmox-testing.md) for the reproducible CI tests. These results are specific to the tested Proxmox version and ACLs.

## Trust boundaries

1. **Vault administrator** manages plugins, mounts, issuer passwords and ACL policies.
2. **Vault credential consumer** authenticates with a narrowly scoped Vault identity and requests `<mount>/creds/<role>`.
3. **Proxmox restricted user** owns the generated token, with the permissions assigned to that user by Proxmox.
4. **Vault external plugin** signs in using that same restricted user's password, receives an ephemeral Proxmox login ticket, and creates/deletes only that user's tokens.

No production workload receives the issuer password. The token secret returned by Vault is independently generated by Proxmox and has its own native expiry.

### Implemented controls

- **Same-user issuance enforcement:** Config `user`/`realm` must match role `user`/`realm`; errors occur before any network request.
- **No root issuance:** Roles targeting `root@pam` are prohibited, and the plugin cannot issue for that account through a different issuer.
- **Password-ticket authentication:** `auth_method=password` logs in afresh per operation, avoiding cached expired tickets. The password is stored in Vault's protected mount config and omitted from read output.
- **Legacy API-token authentication:** Still accepted for **same-user** operations. Historical cross-user mounts can revoke outstanding leases but cannot create more of them.
- **Credential-mode isolation:** Password and API-token issuer credentials cannot be combined in one mount.
- **Finite lifetime:** Role TTL is validated, Proxmox native expiry is set, and Vault leases are nonrenewable.
- **Verified HTTPS:** TLS verification is on by default; `ca_cert_pem` supports internal CAs. Never enable the legacy bypass for production.
- **Role acknowledgement:** `inherit_user_privileges=true` is required; generated token has `privsep=false` and inherits **the restricted user's permissions**.
- **Immutable revoke target:** Each new lease stores the Proxmox target user/realm and token ID, so later role edits do not redirect revocation.

### Residual limitations

| Risk | Status / mitigation |
|---|---|
| Proxmox account has more rights than intended | Restrict and audit **account ACLs**; generated tokens inherit every effective permission |
| Account token can mint its own replacement | Real test denied this with `PVEAuditor`; independently test actual production roles and Proxmox version |
| Issuer password compromise | Vault mount configuration is sensitive; enforce Vault ACL separation, audit, rotation and seal protection |
| Issuer password rotation while old leases exist | Update stored password promptly and verify revocations; old lease metadata does not pin historical auth |
| Proxmox network unavailable during revoke | Retry/reconcile; native Proxmox expiry is the last-resort safety limit |
| Crash between Proxmox token creation and Vault lease registration | An orphan may persist until native expiry; periodic reconciliation by token prefix is not implemented |
| Existing legacy cross-user leases | Can revoke with old issuer if it retains necessary authority; new cross-user issuance is blocked |
| Per-token ACL assignment | Not implemented; this plugin creates `privsep=false` tokens; use narrowly scoped account ACLs |
| Vault HA/plugin recovery | Keep checksum-verified external binary on every Vault node; snapshots do not include executable |

## Proxmox identity setup

Create a separate restricted account for every capability boundary. For example, use `deployer@pve` for VM actions and `images@pve` for template/image actions, with **separate passwords, ACLs and Vault mounts**. Do not run the issuer as a general Proxmox administrator or `root@pam`.

The password is inherently more sensitive than an expiring generated token: the password can log in as the restricted user and create new tokens. Store and rotate it accordingly. Do not print it in logs or pass it through untrusted build artifacts.

## Vault policies

Grant each consumer only:

```hcl
path "proxmox-deploy/creds/deployer" {
  capabilities = ["read"]
}
```

A separate image consumer gets its own exact path. Never grant consumers `config`, `role/*` or Vault system plugin-management permissions. Operators with access to `config` can replace the issuer password and require stronger authentication and auditing.

Do not store generated API tokens in Terraform state, CI output variables, shell history, central logs or tracing spans. Capture the returned lease ID and revoke it on completion, error or cancellation.

## Pre-production acceptance checklist

1. Compile and test the pinned plugin artifact, including `go test -race ./...`, and verify SHA-256 on every Vault host.
2. Verify the deployed Vault runtime loads the plugin and the API hostname validates against the approved TLS CA.
3. Verify the issuer account is restricted to only the planned Proxmox resource paths; it must not have global user/ACL administration.
4. Configure a mount with `auth_method=password` and the exact same user/realm as its role; issue and revoke a disposable credential.
5. Attempt a cross-user credential read; Vault must reject it before Proxmox token creation.
6. Attempt to mint a sibling token with the generated credential; Proxmox must deny it.
7. Attempt user/ACL changes and unrelated VM/storage operations; Proxmox must deny them.
8. Verify separate image/deployment users and mounts have no unintended access to one another.
9. Validate native Proxmox expiry without Vault and explicit Vault lease revoke with actual token removal.
10. Update/delete a role after issuing a token and confirm its historical lease revokes the original account's token.
11. Test issuer password rotation, Vault plugin restart, HA failover and revoke retries.
12. Document the exact Proxmox version, role ACLs, plugin binary digest, test evidence and rollback procedure.

A passing CI test is not a production certificate. Keep live deployment changes separate from plugin source changes and review them independently.

## Legacy migration

Previously configured cross-user mounts **stop issuing new tokens** under the hardened code. Revoke existing leases while their original broad issuer can still delete old tokens. Replace each workload category with its own restricted Proxmox account and password-based Vault mount; verify that historical leases have been removed before retiring the former issuer. See [deployment migration](deployment.md#migrating-from-the-legacy-cross-user-configuration).
